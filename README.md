# HTML RVM

HTML RVM — независимая браузерная виртуальная машина Модели Отношений (Relation Model VM). Проект находится на стадии архитектурного bootstrap: **R0/E1 и ограниченный Natural JSON J1 приняты; полный production VM ещё не реализован**.

## Единая MO Studio

**[Открыть HTML RVM](https://netkeep80.github.io/html_rvm/)** — Natural JSON, асеть дуплетов, контекст E/O/R/S, действительные Run/Step и рефлексия J1/E1. Дуплет обладает собственной идентичностью; B/E могут адресовать другие отношения. Это ограниченная исследовательская реализация, не полный production VM и не выбор окончательного носителя.

Старые пользовательские маршруты перенаправляются в единую Studio. Исторические тесты S1A и R0/V1–V3 сохранены в репозитории и запускаются в изолированном тестовом пакете, но не публикуются как альтернативный интерфейс. [План миграции](docs/UNIFIED-STUDIO-MIGRATION.md).

## Версия проекта

**Версия в формате `XX.YY`**: `XX` — авторски принятая совместимая архитектура, `YY` — число merge в `main` с момента её принятия (`XX.00` — сам архитектурный baseline). Номер автоматически вычисляется из истории Git при публикации сайта — его не нужно менять вручную. **Текущая версия всегда показывается в шапке веб-панели и в [файле VERSION](https://netkeep80.github.io/html_rvm/VERSION).**

Проверить номер в полном Git-клоне на `main`: `npm run rvm:version`. [Полное правило и исторические контрольные точки](docs/VERSIONING.md).

## Назначение

Сохранить семантику jsonRVM/phprvm (сущности, отношения, контексты исполнения, ссылки, программы как данные), но не переносить зависимость от локальных файлов, PHP eval или C++ адресов памяти.

HTML RVM не реализует и не импортирует криптографию, криптоцепочки, физические адреса (ID,H) или HTML DBMS. Работа с JSON организована через DocumentPort/1, чтобы VM могла одинаково запускаться с MemoryDocumentProvider, обычным файловым провайдером и внешней DBMS.

**Принцип исполнения:** HTML RVM работает над отдельным временным изменяемым JSON-состоянием, инициализированным из неизменяемого снимка провайдера. Исполнение отношений может самомодифицировать этот JSON с высокой частотой; ни одно такое изменение само по себе не пишет в DBMS. Сохранение представляется отдельной явной сущностью/намерением Модели Отношений и проходит через доверенный хост с отдельной writer capability. Автоматической записи после каждого изменения или завершения исполнения нет.

HTML DBMS остаётся самостоятельной JSON-СУБД и не импортирует HTML RVM. Их сочетание обеспечивается необязательным внешним адаптером; Root Registry не является частью ядра VM.

## Состояние

- Автором **принята архитектура S0 и интерфейсный проект DocumentPort/1 (23.11.2026)**. Интерпретатор VM пока отсутствует; первый read-only MemoryProvider и тесты временного JSON создаются в [S1A Draft](docs/S1A-MEMORY.md) и не являются полным conformance или релизом. [Точная приёмка S0](docs/BOOTSTRAP-ACCEPTANCE.md).
- Канонические нормативные требования — в каталоге requirements/*.rg.yaml. Остальные документы объясняют и иллюстрируют их, но не заменяют. Нормализация гранулярности требований ведётся отдельным candidate-срезом: [REQ-NORM-001](docs/REQUIREMENTS-NORMALIZATION.md), [glossary](docs/GLOSSARY.md); accepted S0 authority при этом не меняется автоматически.
- RepoGuard v6.0.1 подключается через immutable commit SHA; первый PR содержит bootstrap-требования и требует отдельной проверки первоначальной authority.
- Нет принятого production приложения, готового интерпретатора VM или DBMS адаптера. S1A runtime-тесты охватывают только прямо указанный read-only и working JSON срез; полное соответствие DocumentPort/1 ещё не доказано.
- Тестовая браузерная среда S1A («Счётчик», «Касса», инкремент и редактирование JSON) включена в **PR #5**; её workflow публикует GitHub Pages **только из main** после прохождения тестов. Это не интерпретатор МО и не production Studio.
- Первый предполагаемый потребитель — обезличенная касса; второй — склад.
