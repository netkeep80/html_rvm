## Сценарии интерфейса

1. **Исходный JSON:** редактировать строку (или выбрать «Счётчик», «Касса», загрузить локальный JSON-файл), затем нажать «Создать снимок». Некорректный JSON отвергается без разрушения существующей успешной сессии. Ограничение импорта файла 2 МБ.
2. **Рабочий JSON:** после открытия snapshot материализуется совершенно отдельная изменяемая JSON-модель. Можно изменить весь текст рабочего JSON и вручную применить, не трогая provider snapshot.
3. **Адресные операции:** RFC6901 JSON Pointer `/counter`, `/balance`, `/meta/version` и экранирование `~0/~1`; локальное увеличение, установка JSON-значения, удаление. Значения `null` и отсутствующее поле различаются; неканонический индекс массива отвергается.
4. **Стресс:** кнопка «1 000 000 изменений в RAM», отсчёт операций и время браузера (не производительность VM и не обещание 1e6/с). Нет вызовов `DocumentWriter`, хранилище отсутствует.
5. **Сравнение/диагностика:** исходный snapshot и рабочая модель сравниваются, отдельная проверка неизменности snapshot, сообщения об ошибках и ограниченный журнал (не сохраняемый).
6. **Сброс/экспорт:** сброс создаёт новую рабочую копию из pinned snapshot. Только пользовательский клик «Экспорт» формирует локальный .json-файл через Blob; в DBMS ничего не загружается.

## Правила безопасности и ограничения

- Статический браузерный JavaScript без backend, без внешних runtime/CDN и без сети для пользовательских JSON. Единственный необязательный HTTP-запрос — локальный `build-info.json` для отображения SHA публикации.
- Никаких `localStorage`, `IndexedDB`, cookies, service workers, implicit save, `eval()`, выполнения пользовательского JS и подстановки содержимого JSON в HTML-разметку.
- `source` — только экземпляр read-only MemoryProvider; `working` — mutable session. UI JSON Pointer НЕ расширяет DocumentPort/1, по-прежнему whole-document `read(snapshot, documentId)`.
- Вкладка и память страницы исчезают при перезагрузке. Экспорт файла — отдельное явное действие в браузере; он не является HTML DBMS commit.
- Статус «DRAFT · PR #5» и точный короткий SHA видны в интерфейсе; `published=false` канонических требований **не меняется**, публикация тестового стенда не есть релиз VM.

## Проверки перед авторской приёмкой

- `tests/playground-operations.test.mjs`: правильные/ошибочные JSON Pointer, массивы, литералы, prototype pollution, изменение и изоляция, стресс и недействительные входы.
- `tests/playground-pages.test.mjs`: наличие UI-контролов, отсутствие запрещённых сторонних JS/imports, сборка точного artifact, связь относительных путей и pin GitHub Actions.
- Сохранить все 20 прежних S0/S1A тестов зелёными; проверить RepoGuard exact BASE/HEAD и отсутствия новых диагностик. Успешная сборка статического сайта — **не замена** ручному тестированию в браузере.
- Ручные шаги: открыть ссылку → «Увеличить» → проверить, что source не меняется → «Проверить изоляцию» → «1 000 000 изменений» → «Сброс» → «Касса» и «Создать снимок» → путь `/balance` → установить `null` и увидеть ожидаемую ошибку при числовом инкременте → экспорт локального JSON.
- Независимый READ-ONLY аудит новой delta (UI + workflow + tests) по точному SHA, затем отдельная авторская приёмка. **Никакого merge PR #5 без решения автора**.

Применимость: ручной тестовый стенд S1A, не полноценная МО и не проверка криптографической целостности HTML DBMS.
