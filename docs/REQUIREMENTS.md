# Требования — язык и authority

Единственный нормативный источник: versioned requirements/*.rg.yaml в формате repo-guard/requirement-v1. Тексты в README, документах и Issues — объяснения, но не вторые нормативные требования.

Система IDs: HRVM-PRODUCT-000, HRVM-PROJECT-000, HRVM-ARCH-001, HRVM-PORT-001, HRVM-SNAP-001, HRVM-READ-001, HRVM-WRITE-001, HRVM-REF-001, HRVM-ADAPT-001, HRVM-SEC-001, HRVM-TEST-001, HRVM-CASE-001, HRVM-LICENSE-001, HRVM-BOOT-001.

Иерархия: PRODUCT — корневая предметная цель. PROJECT — дисциплина управления; ARCH — независимость систем; PORT — минимальный интерфейс; SNAP/READ/WRITE — его наблюдаемая семантика; REF — семантика RVM; ADAPT — DBMS интеграция; SEC — граница доверия; TEST — свидетели; CASE — применение на обезличенной кассе и складе; LICENSE — самостоятельная лицензия распространения; BOOT — проверяемые структурные границы начальной спецификации, не проверка всей дисциплины governance.

Статус всех новых требований: **candidate / pending explicit author acceptance**. Жизненный цикл в YAML отражает отсутствие принятия; успешный CI и создание PR не изменяют этот статус.

Требования описывают наблюдаемый результат и границу полномочий, не предписывают ненужную реализацию или полную файловую систему. Отношения документов/реализации связывают конкретные tracked Resources; verified_by используется только при наличии исполняемого теста соответствующего утверждения.

Критерии приёмки изложены в docs/DOCUMENT-PORT-1.md (C01–C15). До реализации это план испытаний, а не доказательство. Точное различение planned / implemented / tested обязательно.

Тест `tests/bootstrap-contract.test.mjs` проверяет только структуру документации, TypeScript-декларации, имена и отношения требований, явно запрещённые импорты и закрепление RepoGuard. Он не подтверждает факт авторской приёмки, полноту графа зависимостей или поведение RVM. Отдельный `HRVM-BOOT-001` ограничивает scope `verified_by` именно этим исполняемым наблюдением.

Для первого PR RepoGuard BASE содержит только LICENSE и не имеет требований; компилятор оценивает BASE и HEAD, поэтому полный GREEN возможен только после отдельного корректно принятого baseline/transition. Это намеренный bootstrap gap, а не повод ослаблять проверку или объявлять её пройденной.

Практический порядок: 1) авторское принятие архитектуры и authority; 2) закрытие bootstrap causal gap; 3) MemoryProvider и contract tests; 4) VM runtime; 5) DBMS adapter и независимая модификация DBMS при доказанной необходимости.
