# DocumentPort/1 — проект межслойного интерфейса

Статус: **S0 CONTRACT DESIGN AUTHOR_ACCEPTED 2026-11-23**; реализация и поведенческая конформность НЕ подтверждены. Нормативные требования — requirements/*.rg.yaml; декларации — ports/document-port.d.ts. [Авторское решение и initial BASE gap](BOOTSTRAP-ACCEPTANCE.md).

## 1. Назначение и граница

DocumentPort/1 передаёт JSON-документы, непрозрачные снимки и необязательные предложения атомарных изменений. Здесь нет понятий МО, физического (ID,H), криптографии, HTML, каталогов и исполнения программ.

Принятое решение S0: `read(snapshot, documentId)` возвращает целый JSON-документ. **JSON Pointer RFC 6901, включая навигацию внутри документа, выполняется только в RVM** после чтения. `root`/alias, `pointer` и контекстные ссылки не являются параметрами публичного DocumentReader. Это отличает DocumentPort/1 от обсуждавшегося RVMDataSource v0.1; два параллельных контракта не вводятся.

**Граница гранулярности чтения и доступа:** минимальная единица, которую `DocumentPort/1` передаёт вызывающему коду, — целый JSON-документ. Порт не предоставляет частичного чтения или отдельной capability на JSON-поле. Если отдельные поля нужно скрывать от приложения, доверенный хост должен не выдавать ему доступ к этому документу; для независимых прав доступа данные следует разделять на документы либо отдельно специфицировать более узкий интерфейс. Выполнение JSON Pointer в RVM не создаёт ограничения доступа: получив документ, RVM уже имеет его целиком.

**Снимок провайдера не является рабочей моделью.** `read(snapshot, documentId)` доставляет независимое JSON-значение из зафиксированной версии; RVM может материализовать его в собственную временную изменяемую рабочую модель. Самомодификация рабочего JSON при исполнении отношений не вызывает `DocumentWriter` и не изменяет исходный snapshot. Никакая реализация адаптера не должна отображать каждую рабочую мутацию на физическую запись или JSON Patch хранилища.

**Явное сохранение:** специальная сущность/намерение МО (временное обозначение `PersistenceIntent`; формат остаётся открытым) создаёт `ChangeRequest` для доверенного хоста. Это не метод `DocumentReader` и не часть физического DBMS API; `DocumentWriter.commit` предоставляется отдельно и только после политики/подтверждения хоста. Обязательна версия base; сохраняется выбранное состояние или явно описанное изменение, а не вся временная история исполнения. Исполнение такой сущности само по себе не наделяет capability записи.

Три базовые операции: openSnapshot(), read(), commit(). Последняя принадлежит отдельной необязательной capability writer; интерпретатор RVM не вызывает commit по факту вычисления отношения.

**S1A (частичная реализация, ещё Draft):** [read-only MemoryDocumentProvider и временные рабочие JSON-сессии](S1A-MEMORY.md). Нет writer, CAS, DBMS parity или исполняемой МО. S0 контракт не меняется; статус выполненных проверок относится только к узкому S1A.

## 2. Наблюдаемая семантика

openSnapshot(reference?): фиксирует согласованный снимок документов данного provider instance. Отсутствие reference означает текущий доступный снимок в момент операции. Переданная строка — непрозрачный для потребителя provider-specific locator; переносимость между реализациями НЕ гарантируется. Выдаваемый snapshot — handle привязанный к конкретному provider instance. Он не является физической криптографической capability, абсолютным временем или обещанием latest. Другой instance обязан отвергнуть чужой handle. Открытый snapshot не меняется от чужого commit.

read(snapshot, documentId): возвращает JSON-значение, адресованное стабильным документным ID в выбранном снимке. Результат отделён от внутренних объектов провайдера; модификации результата не влияют на снимок. Чтение не создаёт документа, не фиксирует изменение и не меняет видимые данные. Провайдер может выполнять внутреннее ленивое чтение и кэширование, не нарушая наблюдаемую чистоту.

commit(base, changes): доступно только доверенному host по отдельному writer. Успех публикует один новый согласованный snapshot всего набора изменений. Патчи RFC 6902 в рамках каждого документа применяются последовательно; один документ может встретиться в списке changes только один раз. Создание/удаление документов и переименование/перенос виртуальных файлов НЕ являются частью v1. Все целевые документы должны существовать в base.

При ошибке commit не публикует частичное обновление. В рамках одного провайдера commit от устаревшего base (не совпавшего с его current snapshot) должен завершаться CONFLICT, без молчаливого перезаписывания. Write implementations без compare-and-publish не могут объявить соответствие DocumentPort/1 Writer. У read-only реализаций writer может отсутствовать.

## 3. Типы

~~~typescript
interface DocumentReader {
  openSnapshot(reference?: string): Promise<SnapshotHandle>;
  read(snapshot: SnapshotHandle, documentId: string): Promise<JSONValue>;
}
interface DocumentWriter {
  commit(base: SnapshotHandle, changes: readonly DocumentChange[]): Promise<SnapshotHandle>;
}
interface DocumentChange {
  documentId: string;
  patch: readonly JSONPatchOperation[];
}
~~~

Точные draft-декларации см. ports/document-port.d.ts. SnapshotHandle opaque в смысле authority/identity, не сериализуемое обязательное пользовательское значение. Наличие метода commit у объекта RVM не означает разрешения использовать writer; host отдельно предоставляет writer только в доверенном контексте.

## 4. Ошибки (стабильные машинные коды)

- NOT_FOUND — неизвестный documentId внутри снимка.
- INVALID_REFERENCE — неверный documentId, locator или snapshot handle.
- SNAPSHOT_UNAVAILABLE — указанный snapshot более недоступен или не может быть воспроизведён.
- INTEGRITY_FAILURE — обнаружен конфликт криптографической / структурной целостности у защищённого провайдера.
- ACCESS_DENIED — отсутствует явная capability, политика запрещает операцию.
- INVALID_PATCH — patch не соответствует RFC 6902 или допустимой схеме; без побочных публикаций.
- CONFLICT — base устарел для данного провайдера, target не совпал с current.
- RESOURCE_LIMIT — лимит размера, глубины, количества объектов или времени.
- UNSUPPORTED — провайдер не поддерживает требуемую операцию/исторический locator.
- INTERNAL — непредвиденный отказ; не скрывать причину под NOT_FOUND.

Ошибки не передают приватные (ID,H), plaintext скрытых документов, секреты или точные структурные сведения, если они не разрешены данным host policy.

## 5. Связанные гарантии

- read(A,d) дважды возвращает одинаковое JSON-значение при одном A,d, если операция успешна; сравнение семантическое (JSON-структура).
- read(A,d) и read(B,d) могут различаться; commit не изменяет прошлый A.
- Результат read может быть mutable copy, но не ссылкой на внутреннее state.
- `JSONValue` как TypeScript-тип недостаточен для runtime-проверки. Любое значение на границе `read` и `commit` должно принадлежать строгому JSON-домену: `NaN`, `Infinity`, `-Infinity`, `undefined`, `BigInt`, функции и циклические структуры отвергаются; отсутствующий ключ не подменяется `null`. Числа должны быть конечными. Правила безопасного разбора и сериализации требуют отдельных реализационных тестов.
- JSON Pointer и ссылки МО обрабатывает VM после read; DocumentPort не содержит метода resolve.
- Чистое вычисление VM при одинаковом наборе данных, VM runtime и контексте должно дать одинаковый результат независимо от провайдера.
- Provider может быть offline, memory, file, IndexedDB, DBMS: их возможности чтения и записи объявляются явно.

## 6. Сценарии / contract test matrix (план, НЕ результаты)

C01: две последовательные read одного A,d дают равные JSON.
C02: изменённый вручную JSON-результат read не влияет на следующую read.
C03: неизвестный d даёт NOT_FOUND без создания.
C04: snapshot A после успешного commit в B сохраняет прежнее значение.
C05: два документа меняются одним commit, оба видимы в B.
C06: ошибка второго patch приводит к отсутствию публикации изменений обоих документов.
C07: два commit от одного base: только первый может победить; второй получает CONFLICT.
C08: недействительный/чужой handle отвергается.
C09: read-only RVM работает без writer и без DBMS.
C10: одинаковая логическая модель и чистый runtime дают parity Memory/DBMS.
C11: повреждение цепочки даёт INTEGRITY_FAILURE, а не синтетический документ.
C12: попытка заставить VM выполнить код или запись без выдачи host capability отвергается.
C13: непроверенный head не выдаётся как валидный документ.
C14: путь alias переименован, documentId остаётся стабильным.
C15: исторический snapshot не становится latest сам по себе.
C16: поддельный snapshot handle и handle другого экземпляра провайдера отвергаются.
C17: передача snapshot handle через iframe/Worker без доверенного механизма делегирования не создаёт authority и не позволяет прочитать документы.
C18: не-JSON значение (`NaN`, `Infinity`, `undefined`, `BigInt`, функция, цикл) отвергается на всех обязательных границах read/commit.
C19: полнодокументный `read` не зависит от JSON Pointer; тест разрешения RFC 6901 расположен в RVM, а не в провайдере.
C20: восстановление/открытие snapshot, материализация рабочей копии и её многократная самомодификация не изменяют исходный snapshot и read(snapshot, d).
C21: стресс-сценарий с большим числом внутренних JSON-изменений (вплоть до миллиона операций) приводит к нулю вызовов provider writer/DBMS без явного запроса; это тест границы эффектов, не обещание throughput.
C22: завершение программы, получение вычисленного результата и периодический тик не вызывают автоматического сохранения.
C23: явная сущность намерения сохранения формирует нейтральный ChangeRequest с base snapshot и выбранным эффектом; при отсутствии writer она не вызывает commit.
C24: только разрешённый host ChangeGateway может выполнить commit после проверки политики; отклонение/конфликт не публикуют частичного результата.
C25: два исполнения от общего immutable snapshot имеют изолированные mutable working states; их изменения не влияют друг на друга.
C26: сохранённый результат не обязан содержать поток промежуточных мутаций; сохраняется только явно выбранный эффект, совместимый с `DocumentWriter`.

## 7. Открытые решения (не подменять умолчаниями)

- Переносимый SnapshotLocator, TTL handles и сериализация между iframe/Worker.
- Согласованность/изоляция при нескольких вкладках, нескольких автономных HTML-копиях, IndexedDB.
- Создание, удаление, перемещение документов и migration identity.
- Доказательство доверенного provenance runtime, публикация anchor/head и multi-user sync.
- Конкретная DBMS JSON-document policy и Root Registry schema (вне ядра VM).
- Фиксированные ресурсы VM (глубина, инструкции, CPU) и модель эффектов.
- Формат сущности PersistenceIntent и ChangeRequest, явная выборка результата и границы жизненного цикла рабочего JSON; это S1/S2, а не новая физическая политика DBMS.
