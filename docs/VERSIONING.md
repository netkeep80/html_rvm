# Версионирование HTML RVM — XX.YY

Статус: **кандидат правила VERS-001** до независимого аудита и авторской приёмки точного PR. [Issue #7](https://github.com/netkeep80/html_rvm/issues/7).

## Правило

**XX** — номер совместимой архитектуры (две цифры 01–99). Его изменение означает принятие новой **несовместимой** архитектуры отдельным авторским решением, а не просто добавление возможностей.

**YY** — порядковое число штатных **двухродительских merge-коммитов на первой родительской линии main** после принятого baseline архитектуры XX; диапазон 00–99. Сам архитектурный baseline есть **XX.00**. Каждый следующий merge в main увеличивает YY ровно на один — независимо от количества коммитов в PR, файлов или характера изменений (код, тесты, документация). Сортировка по датам или номеру PR не используется.

Первый принятый архитектурный baseline:
- Архитектура: **01**
- Принятая версия **01.00**, [PR #2](https://github.com/netkeep80/html_rvm/pull/2)
- **main merge baseline SHA:** 406577bcf06b2c43cccbc2ef664fad875668136b.

Конкретный проверенный исторический пример:

| main merge | Версия |
|---|---|
| PR #2 — принята XX=01 | 01.00 |
| PR #5 — MemoryProvider и JSON Lab | 01.01 |
| PR #6 — ссылка в README | 01.02 |

При слиянии версии VERS-001 следующим штатным merge в main получится 01.03, **если между проверкой и merge не будет других merge**. Результат всегда определяется из фактического post-merge SHA, не вычисляется заранее на доверии.

## Один источник истины

В репозитории лежит только конфигурация **version-policy.json**: номер архитектуры, точный SHA её принятого merge и правило подсчёта.

Команда из корня **полного Git-клона на main**:

    npm run rvm:version

Она исполняет tools/version.mjs, читает реальный первый родительский путь Git до принятого baseline и вычисляет XX.YY. Не хранится вручную обновляемый номер YY в git-файле: он был бы устаревшим сразу после следующего merge.

**Обязательная конвенция основной ветки:** изменения main включаются штатным двухродительским merge-коммитом (GitHub Merge pull request). Прямой commit, squash/rebase, octopus merge, отсутствие baseline в first-parent chain или shallow history **блокируют вычисление и публикацию**, вместо выдачи ошибочного номера. Подтверждать правило обычным CI; при возможности закрепить разрешённый метод merge в branch ruleset.

Если YY достигнет 99, следующий merge блокируется расчётом до отдельного авторского решения о расширении формата или архитектуре. Принятие новой несовместимой архитектуры (XX+1) требует отдельной записи архитектурной приёмки и привязки нового SHA baseline; нельзя переобъявить XX по удобству или автоматически при переполнении счётчика.

**Private Node package.json не содержит SemVer-version.** XX.YY — собственный формат версии HTML RVM, не NPM SemVer; не поддерживать второй расходящийся счётчик.

## Веб-панель GitHub Pages

Workflow .github/workflows/pages-preview.yml запускается **при каждом push в main**, а не только при изменениях UI. Checkout использует fetch-depth: 0; Git история должна содержать принятую базу. Сборка сначала проверяет версию для точного GITHUB_SHA, затем публикует:

- Статический /VERSION в корне GitHub Pages — текст XX.YY для машинной и ручной проверки.
- /site/build-info.json — поля version, commit, branch, preview.
- HTML JSON Lab показывает **vXX.YY в шапке** и **Версия XX.YY · HEAD SHA внизу**. Если метаданные отсутствуют или некорректны, показывается «Версия недоступна»; никаких придуманных fallback-версий.

Статус S1A · TEST LAB сохраняется независимо от версии: нумерация релизного кода **не означает**, что интерпретатор отношений, DBMS adapter или PersistenceIntent реализованы либо опубликованы как production.

## Проверяемые свойства

- Архитектурный baseline 01.00, PR #5 01.01, PR #6 01.02.
- Следующий merge 01.03; изменение исходного/рабочего JSON в браузере на номер версии не влияет.
- Разные количество коммитов и файлов PR не увеличивают YY внутри PR.
- Ошибочные SHA/invalid policy, отсутствующая история, прямые main commits, squash, octopus merge и overflow должны завершаться ошибкой.
- Версия генерируется из исходного Git-лога при Pages build, а не из JavaScript в клиенте и не из GitHub API.
- Проверки должны оставаться зелёными и без изменения S0 DocumentPort/1 и lifecycle.

**Ограничение доказательства:** до настоящего merge тестовая ветка содержит обычные development commits, поэтому историческая проверка текущего main и отрицательные сценарии выполняются как чистые тесты (плюс временный Git-репозиторий); фактическая версия опубликованной веб-панели проверяется отдельно только по post-merge main deployment.
