# Архитектура HTML RVM — принятый S0 baseline / BOOT-001

Статус: **AUTHOR_ACCEPTED 2026-11-23** (только архитектура; runtime не реализован). Нормативная authority: requirements/*.rg.yaml. [Решение и bootstrap-gap](BOOTSTRAP-ACCEPTANCE.md).

## 1. Два независимых продукта и необязательный адаптер

    html_rvm                         html_dbms
       ^                                ^
       |  DocumentPort/1                | DBMS native API
       +------------ adapter -----------+
                      ^
                      |
               host / cash_app

HTML RVM: идентичность сущностей, тройки subject/relation/object, исполнение отношений, контексты, лексический/контекстный resolver, адресация внутри документа, проекции и представления. Она не импортирует HTML DBMS.

HTML DBMS: хранение JSON, версии, цепочки, шифрование, проверяемый replay, JSON Patch, публикация и диагностика. Она не импортирует HTML RVM и не интерпретирует $sub, $rel, $obj.

Adapter: преобразование documentId и непрозрачного snapshot в специфичный для поставщика доступ, Root Registry для DBMS, проверка genesis/ancestry, организация нескольких head и trusted write admission. Он не принадлежит ядру ни одного продукта.

Host: выдача capability чтения/изменения, проверка прав и полномочий, явное подтверждение эффектов, доверие к исполняемому коду и управление жизненным циклом приложения.

Никакой обязательной файловой иерархии в RVM нет: виртуальный путь — возможный alias стабильного documentId, обрабатываемый провайдером/каталогом. Виртуальный файл — именованное представление JSON-документа. Сущность МО внутри документа не тождественна документу и не тождественна head криптоцепочки.

## 2. Отделение рабочего JSON от версионированного хранилища — обязательный инвариант

HTML RVM **не исполняет МО непосредственно над криптографической цепочкой HTML DBMS, объектом хранилища или опубликованным snapshot**. Адаптер сначала получает доверенно восстановленное JSON-состояние через `DocumentPort/1`, затем RVM создаёт из него **отдельную временную изменяемую рабочую модель** (working JSON state). Открытый snapshot провайдера — неизменяемая исходная версия и ссылка на происхождение; рабочее состояние — другая область памяти и жизни.

```text
DBMS verified/replayed JSON → immutable provider snapshot
                                      │ materialize / detach
                                      ▼
                            transient mutable JSON working state
                                      │ self-modifying relations
                                      ├── potentially millions of in-memory changes
                                      ├── intermediate states / computations
                                      └── explicit PersistenceIntent entity in MO
                                                  │
                                      trusted host / ChangeGateway
                                                  │ authorize/validate/confirm
                                                  ▼
                                   optional provider writer → DBMS commit
```

Модель Отношений исполняется через **самомодификацию рабочего JSON**. Даже очень частые промежуточные изменения не создают `JSON Patch`/commit событий в HTML DBMS, не обновляют исходный snapshot, не изменяют опубликованный head и не вызывают автосохранение по таймеру либо при завершении исполнения. Производительность внутреннего исполнения не связывается с частотой криптографических записей. Формулировка «миллионы изменений в секунду» описывает проектный режим высокой частоты, но не утверждает пока измеренный показатель.

**Сохранение — явная сущность/намерение в языке МО** (условное имя `PersistenceIntent`, точная JSON-схема и синтаксис открыты). Такая сущность указывает *что* предлагается сохранить и *от какой исходной версии*; её интерпретация формирует нейтральный `ChangeRequest`. Она не несёт прямую DBMS capability и не означает разрешения на запись. Только доверенный host/ChangeGateway принимает решение, выдаёт `DocumentWriter` и выполняет разрешённый commit. Ядро RVM не знает AES-GCM, физических (ID,H), Root Registry и DBMS API. Если writer недоступен или host отклонил запрос, рабочая модель может продолжать исполнение без изменения опубликованных данных.

При явном сохранении сохраняется только **выбранное состояние или явно определённое изменение** в форме, допускаемой текущим контрактом записи; весь поток промежуточных самомодификаций **не обязан** логироваться или реконструироваться. Изменения сохраняются относительно зафиксированного base snapshot с политикой конфликтов. Согласованность многодокументного commit требует отдельной проверки. Новые данные после commit не подменяют уже открытый исходный snapshot и не перезаписывают автоматически текущую рабочую модель.

## 3. Три вида идентичности

- Entity ID: логический идентификатор сущности и её положение в документе, интерпретируемое RVM.
- Document ID: стабильная идентичность JSON-документа, объявляемая его провайдером. Не зависит от пути, имени, версии.
- Snapshot: фиксированный согласованный набор версий документов, непрозрачный для VM.

Физическая DBMS capability (ID,H) полностью скрыта в DBMS-адаптере. Если перенос сущности между документами должен сохранять глобальную идентичность, это отдельное требование к индексу; в BOOT-001 не предполагается.

## 4. Версионируемый Root Registry в DBMS-адаптере

Один вариант хранения Root Registry — обычное воспроизводимое JSON-состояние main chain:

~~~json
{
  "documents": {
    "doc:cash-transactions": {
      "genesis": "GENESIS_HASH",
      "head": ["PHYSICAL_ID", "PHYSICAL_HASH"]
    }
  },
  "paths": {
    "/data/transactions.json": "doc:cash-transactions"
  }
}
~~~

Пример схематический, НЕ является форматом HTML_DBMS/2.2 и не обязателен для MemoryProvider. Genesis identity фиксируется отдельно от изменяемого head; по необходимости уникальность genesis гарантируется nonce. Перемещение/переименование path не меняет documentId.

Версия модели V — выбранный, доверенно открытый main snapshot. Все чтения в ходе одного вычисления привязаны к этому V. Исторический head может описывать корректную старую версию, не обязательно глобально новейшую или авторизованную. Внешний trust anchor потребуется для проверки публикационной актуальности.

## 5. Атомарная публикация

Провайдер с write capability должен обеспечивать локальный all-or-nothing commit для нескольких документов: проверить base snapshot, запретить конфликт, подготовить новые версии, проверить цепочки, затем атомарно опубликовать единый каталог. Запись в физический рабочий контейнер сама по себе не означает публикацию.

Offline fork от другой HTML-копии не распознаётся как глобально устаревший без внешней координации. При неудаче могут остаться недоступные из опубликованного main orphan ciphertext; удаление и восстановление не выполняются автоматически.

## 6. Независимость исполнения и доверия

Cryptographic integrity документа не означает авторизацию программы. Runtime/host должны быть доверены независимо и запускать код только по явной политике, в песочнице с минимальными полномочиями. Программы МО по умолчанию не получают write capability. Для воспроизводимого отчёта фиксируются логический snapshot, версия/runtime identity, набор разрешённых внешних эффектов.

## 7. Граница текущей реализации HTML DBMS

HTML_DBMS/2.2 имеет только политики main/transaction, жёсткую схему main.tables/tabs и вложенную transaction chain. Для произвольных JSON-документов и множества разных root policies потребуется отдельное общее расширение DBMS, не RVM-specific. BOOT-001 не объявляет существующую реализацию совместимой с DBMSDocumentProvider.

## 8. Альтернативы

A: плоский MemoryDocumentProvider — минимальная эталонная реализация и тестовый оракул; не даёт долговечной криптоистории.

B: отдельная криптоцепочка на документ + Root Registry внутри DBMS-адаптера — целевая интеграция; сложнее commit и replay.

Нельзя подменять контракт A деталями B: переход A→B должен оставлять VM и её JSON-программы неизменными.
